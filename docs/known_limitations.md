# Known limitations

- Sections 6 and 7 and Phase 1 (1A-1D) are complete, with a no-go from zero early valid solutions in the frozen Sudoku setting. Both final holdouts remain reserved. The Phase 2A online hook is implemented; measured development/final comparisons, controller training and later studies remain pending.
- The validated environment is Linux x86_64 / WSL2 / Python 3.12.3 on this RTX 5060. Native Windows/host Python 3.14 inference is unvalidated.
- The full official baseline is 1,725/2,000 (86.25%); paper v1 reports 86.1%. The +0.15 percentage-point discrepancy has no established cause. Exact paper-number/prediction parity is not claimed.
- Existing baseline results retain official solved/cell/valid-grid metrics and have not been independently rescored. Phase 1A implements clue-consistent solution validation; Phase 1B adds full-resolution prefix decoding. All 353 implemented tests pass, including 43 new Phase 2 tests. Final-output parity with the unchanged official evaluator is established on the matched 32-input exploration smoke run, not all platforms/batch sizes.
- Smoke/full YAML configs now drive offline collection with strict partition/budget checks. The stopping-policy YAML remains a proposed template; baseline setup uses the official upstream config.
- Offline JSONL contains 12 levels for 1,000 exploration and 400 development puzzles. No valid output appeared before level 12. The Phase 1 report and scientific figures are complete. Diagnostic profiles cover the first 100 indices of each partition, five repeats each, after ten exploration warmups.
- Every-level verification added an estimated 44.18% development cost (95% interval 43.45%-45.02%). This is a component-sum diagnostic estimate, with instrumentation sensitivity disclosed; it is not measured online latency. Original trajectory timing fields remain null; measured costs are in separate profile artifacts.
- Profiling used batch size 1 versus collection batches up to 128. Intermediate tokens differed on five profiled identities; final tokens/validity matched. The gate uses its own matched batch-one outputs.
- No online stopping hook, trained controller, interactive viewer, or measured adaptive speedup exists. The no-go applies to this frozen checkpoint/reconstruction/sampling setting; other tasks and checkpoints remain untested.
- The selective dataset reader supports the exact pinned protocol-4 integer-list grammar. It reads/checksums raw file bytes and traverses their structure, while materializing only selected token rows. Unsupported serialization formats require explicit revalidation.
- Baseline process durations include loading/scoring and are not inference latency.
- The descriptive evaluator scored reserved holdouts internally; only aggregates were inspected. Future policy selection must follow the frozen phase-specific holdout rules and access disclosures.
- Checkpoints, datasets, caches, the environment, and raw prediction pickles are local/ignored. The dependency lock is platform-specific; another machine must recreate the environment and downloads.
- The authoritative design remains `Anytime_NCM_Design_Document.md`; `DESIGN.md` is a navigation entry point.

- R1A adds a reference-based, exploration-only descriptive error taxonomy. Its final-outcome groups and future reference labels are not stopping features. It does not diagnose a causal tokenizer/generator mechanism or change the original no-go; R1B subsequently completed the separate 32-input target-encoding pilot.

- R1B achieved 32/32 exact final reference round trips but no valid target-encoded prefix before level 12. Its solution-supplied target path is an oracle diagnostic, not a deployable policy or causal isolation of a tokenizer/generator component. The fixed pilot has no population-wide absence guarantee and does not overturn the original no-go.

- R2 found zero early-valid inputs in each of its fixed easy/medium 32-input screens; final validity was 32/32 and 31/32. The screen qualifies neither candidate for R3 and supplies no new Phase 2 go, measured cost benefit, or population absence guarantee. The released-Sudoku first-valid path is closed at this budget.
- Released easy/medium/hard solution files are byte-identical. R2 inherits original row-index partitions across masks, audits candidate puzzle hashes incrementally (including reserved operands), and materializes only 32 exploration puzzle/reference rows per candidate. These are related difficulty views with prior hard exploration exposure, not independent datasets; base-model training overlap remains unknown.
- R2's comparator uses the unchanged pinned official evaluator function bodies on selectively loaded inputs at batch 1. Its 64 exact paired comparisons establish final parity in that screen, not full-set CLI reproduction or all-platform/batch parity. The 128 full-depth input-generation allocation is consumed; there was no R2 profiling, training, or final-holdout evaluation.

- R3 was a separately requested easy-setting extension despite failed R2 entry, not confirmation of a positive screen. It found no early valid output in 1,400 exploration/development inputs and an estimated 39.31% development cost increase (95% interval 38.96%–39.68%); the new gate is no-go. No measured online latency/speedup or population impossibility claim follows.
- R3 reused the 32 easy screen trajectories, preserved shared-solution row reservations, and exposed only official full-baseline aggregates for reserved rows. These difficulty views and prior hard development exposure are related; they are not independent datasets.
- R3 collection had one metadata-write failure before the next model call. A dated amendment preserved all 499 completed rows and resumed 901 unrun inputs within the unchanged budget. No interrupted-process end-state fingerprint exists; the resumed process reloaded the original starting state and matched it at completion. Execution, amendment and report-only sources are recorded separately.

- Phase 2 is a separately requested online experiment despite failed offline opportunity gates. 2A is implemented and parity/true-stop checks pass; development timing and final evaluation remain pending. No practical speedup or offline go is asserted by implementing a hook.
